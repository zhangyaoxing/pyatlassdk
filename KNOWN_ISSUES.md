# Known issues

Defects found while writing the test suites on branch `test/add-test-suites`. **Nothing under
`src/` was changed.** Every item below is pinned by a `strict` xfail test, so the suite stays
green today and fails loudly when an issue is fixed (remove the marker and the entry then).

> `src/pyatlassdk/{admin,app,status}/` is generated by
> [mongo-atlas-sdk](https://github.com/zhangyaoxing/mongo-atlas-sdk). Issues 1–5 originate in
> the generator or its templates and have to be fixed **upstream**, then regenerated. Issues 6–8 are
> in the generated `client.py` template (same upstream fix).

Run the pinned tests: `pytest tests/test_known_issues.py -rx` (plus one case in
`tests/test_resource_contract.py` for issue 5).

| # | Severity | Issue | Scope |
|---|----------|-------|-------|
| 1 | High | `Literal[true]` / `Literal[false]` annotations make models unusable | 8 app models |
| 2 | High | Resource class shadows the model it returns | 3 admin methods |
| 3 | High | Empty successful responses crash with `JSONDecodeError` | up to 107 methods, all 3 clients |
| 4 | High | Non-JSON downloads (gzip / CSV) cannot be read | 6 admin methods |
| 5 | Medium (unverified) | `GET` sent with a JSON body | 1 admin method |
| 6 | Low | Non-JSON / non-object auth responses escape as raw exceptions | OAuth + App login |
| 7 | Low | 3xx responses are not reported as `AtlasApiError` | all clients |
| 8 | Low | App client accepts an empty access token | `AtlasAppAdminClient` |
| 9 | Note | Explicit `None` can never be sent as JSON `null` | all request bodies |

## 1. `Literal[true]` / `Literal[false]` annotations (High)

**What is wrong.** The generator emitted the JSON literals `true` / `false` into Python
annotations instead of `True` / `False`. Because the modules use `from __future__ import
annotations`, import succeeds and the error only appears the first time the model is used.

```python
auto_confirm: Literal[true] | None = Field(default=None, alias="autoConfirm", ...)
```

**Symptom.**
```
PydanticUserError: `PushPullAppConfig` is not fully defined; you should define `true`,
then call `PushPullAppConfig.model_rebuild()`.
```
`__pydantic_complete__` is `False`; instantiation, validation, `model_json_schema()` and
`model_rebuild()` all fail.

**Affected (8 models, `pyatlassdk.app.models`):**
`EmailPasswordAuthProviderConfigVariant1`…`6`, `EmailPasswordAuthProvider` (references the
variants) and `PushPullAppConfig` (references the auth-provider constructor).

**Impact.** Anything that takes or returns these cannot work, notably
`apps.admin_push_app_configuration(body=PushPullAppConfig(...))` and creating or reading
email/password auth providers.

**Tests.** `test_known_issues.py::test_model_with_literal_true_is_usable`,
`::test_push_app_configuration_body_can_be_constructed`. The generic model checks in
`test_models.py` exclude these classes explicitly (`UNRESOLVABLE`).

**Fix upstream.** Render JSON booleans with Python's `True`/`False` when emitting `Literal[...]`.

## 2. Resource class shadows the model it returns (High)

**What is wrong.** `src/pyatlassdk/admin/resources/cluster_outage_simulation.py` imports the model
`ClusterOutageSimulation` and then defines a resource *class with the same name*. The class
statement rebinds the name, so every annotation and `response_model=ClusterOutageSimulation`
refers to the resource class, not the model.

**Symptom.**
```
PydanticSchemaGenerationError: Unable to generate pydantic-core schema for
<class 'pyatlassdk.admin.resources.cluster_outage_simulation.ClusterOutageSimulation'>
```
Reproduced with a valid 200 JSON body from
`client.cluster_outage_simulation.get_group_cluster_outage_simulation(...)`.

**Affected.** `start_`, `get_` and `end_group_cluster_outage_simulation`, i.e. the whole resource.
It is the only such collision among the 89 resource modules (55 admin, 30 app, 4 status). The
`body: ClusterOutageSimulation` parameter of `start_…` is annotated with the wrong type too.

**Tests.** `test_cluster_outage_simulation_resource_returns_the_model`,
`test_cluster_outage_simulation_response_model_is_a_pydantic_model`.

**Fix upstream.** Import the model under an alias (or suffix resource class names, e.g.
`ClusterOutageSimulationResource`) when the names collide.

## 3. Empty successful responses raise `JSONDecodeError` (High)

**What is wrong.** `client.request()` returns `None` only when `response_model is None`.
Otherwise it unconditionally runs `response.json()`. Endpoints declared with
`response_model=Any` (107 methods: 73 `DELETE`, 18 `POST`, 12 `GET`, 2 `PUT`, 2 `PATCH`) are the
"returns whatever / nothing" cases, and a `204 No Content` (or any empty 2xx body) crashes.

**Symptom.**
```python
client.teams.remove_group_team("g", "t")   # server answers 204
# json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0)
```
The delete **succeeds on the server** but the caller sees an exception, so retry logic may repeat
or mask a successful operation. Same code path in `pyatlassdk.app` and `pyatlassdk.status`.

**Tests.** `test_empty_success_body_with_any_model_returns_none` (3 clients × 200/202/204),
`test_remove_team_from_project_handles_no_content`.

**Fix upstream.** In `request()`, return `None` when `response.content` is empty (or the status
is 204) before validating.

## 4. Non-JSON downloads cannot be read (High)

**What is wrong.** Six admin endpoints request `…+gzip` or `…+csv` media types but are declared
`-> str` with `response_model=str`, and `request()` still calls `response.json()` on the body.

| Method | Media type |
|--------|------------|
| `monitoring_and_logs.download_group_cluster_log` | gzip |
| `online_archive.download_group_cluster_online_archive_query_logs` | gzip |
| `streams.download_group_stream_audit_logs` | gzip |
| `streams.download_group_stream_operational_logs` | gzip |
| `data_federation.download_group_data_federation_query_logs` | gzip |
| `invoices.get_org_invoice_csv` | csv |

**Symptom.** gzip bytes: `UnicodeDecodeError: 'utf-8' codec can't decode byte 0x8b`; CSV and
plain text: `JSONDecodeError`. Even with a fix the declared return type `str` is wrong for gzip
(should be `bytes`). Log download is a core Atlas workflow.

**Tests.** `test_log_download_returns_the_raw_payload`, `test_csv_invoice_download_returns_text`,
`test_request_returns_text_for_str_model`.

**Fix upstream.** Choose the decoder from the declared media type: `bytes` for gzip, `response.text`
for CSV / `str`.

## 5. `GET` sent with a JSON body (Medium, needs spec confirmation)

`invoices.search_org_invoice_line_items` (`…/invoices/{invoiceId}/lineItems:search`) issues `GET`
with `json=body`. Bodies on `GET` are not portable: proxies and servers may drop or reject them,
and the `:search` suffix suggests the real operation is a `POST`. **I did not have the OpenAPI
spec available, so confirm the verb against the Atlas Admin API spec before acting.**

**Test.** `test_resource_contract.py::test_get_requests_have_no_body[admin.invoices.search_org_invoice_line_items]`
(strict xfail). It is the only `GET`-with-body method among the 715 generated methods checked.

---

## 6. Auth responses that are not a JSON object escape as raw exceptions (Low)

`AtlasAdminClient._access_token()` and `AtlasAppAdminClient.login()` check the HTTP status and
the `access_token` field, but call `response.json()` unguarded.

* 200 with an HTML/text body (maintenance page, captive proxy) → `json.JSONDecodeError`.
* 200 with a JSON array → `AttributeError: 'list' object has no attribute 'get'`.

Callers catching `AtlasApiError` miss both.

**Tests.** `test_oauth_token_endpoint_with_html_body_raises_atlas_error`,
`…_with_array_body_raises_atlas_error`, `test_app_login_with_html_body_raises_atlas_error`.

---

## 7. 3xx responses are not reported as errors (Low)

`httpx.Client` does not follow redirects by default and `request()` only raises for
`status >= 400`. A `301/302` falls through to JSON parsing and surfaces as `JSONDecodeError` (or
returns `None` when no model is declared), hiding the real cause, e.g. a wrong `base_url`
scheme or host.

**Test.** `test_redirect_response_raises_atlas_error` (3 clients).

---

## 8. Empty access token accepted by the App client (Low)

`AtlasAdminClient` rejects empty credentials with `ValueError`, but
`AtlasAppAdminClient(access_token="")` builds a client sending `Authorization: Bearer `
and fails later with a server 401.

**Test.** `test_app_client_rejects_empty_access_token`.

---

## 9. Explicit `None` is never sent as `null` (Note, by design)

`_serialize()` dumps models with `exclude_none=True`, so a field set to `None` is
indistinguishable from an unset one and the JSON `null` is never transmitted. APIs that clear a
value by receiving `null` (PATCH-style updates) cannot be driven through the typed models.
Passing a raw `dict` as the body is the only workaround. Pinned by the passing characterization
test `test_explicit_none_cannot_be_sent_to_clear_a_field`; decide whether to keep or change it.

---

## Not bugs, but worth knowing

* No retry or back-off on `429` / `5xx`, and no pagination helpers (callers loop on `page_num`).
* Response models are strict about required fields; a field the API starts omitting will raise a
  pydantic `ValidationError` (not an `AtlasApiError`).
* The README claims `AtlasClient` is a backwards-compatible alias — verified, it is.

## How the suites are organized

| File | Covers |
|------|--------|
| `test_package.py`, `test_errors.py`, `test_enums.py` | public surface, error types, enum helpers |
| `test_serialization.py`, `test_request_pipeline.py` | `_serialize`/`_payload`, `request()` for all 3 clients |
| `test_admin_client.py`, `test_app_client.py`, `test_status_client.py` | construction, Digest/OAuth, login, every status endpoint |
| `test_resource_contract.py` | 715 generated methods × ~12 invariants (verb, quoting, params, body, headers) |
| `test_models.py` | structure of all 1,292 generated model modules, lazy exports |
| `test_known_issues.py` | strict-xfail record of the issues above |
